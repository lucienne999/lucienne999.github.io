## Proposed Changes
### 文件 1：`/Users/bytedance/codebase/lucienne999.github.io/.trae/skills/travel-planner/SKILL.md`
- 做什么：
  - 新增旅行 Skill 的 frontmatter，定义稳定的 `name` 与清晰的 `description`。
  - 编写用途、适用范围、不适用范围、触发条件、规划原则、信息收集规则、输出结构、评分规则、示例输入输出。
- 为什么：
  - 让系统在用户提出旅行规划需求时，能稳定调用一个专门面向“休闲恢复型旅行”的 Skill。
  - 将“markdown 富文本”“网络评价”“评分与优缺点”“弹性时间安排”等要求固化为可执行规范，而不是临时发挥。
- 怎么做：
  - 延续现有 Skill 文档格式，frontmatter 使用英文标识，正文以中文编写规范说明。
  - `description` 同时覆盖“做什么”和“何时调用”，避免误触发。
  - 正文明确该 Skill 是“通用旅行规划”而非某个固定城市模板。
  - 在“输入要求”中规定：
    - 优先收集目的地、出行天数、出发地、同行关系、预算范围、偏好节奏、住宿偏好、是否租车/公共交通、避雷项。
    - 若预算未给出，先主动询问预算范围后再生成安排。
  - 在“规划原则”中规定：
    - 优先低压、恢复感、步行强度可控、减少折返与赶路。
    - 行程以半天级组织：上午 / 下午 / 晚上。
    - 每天保留弹性时间，避免将所有时段填满。
    - 至少提供 1 个可替换的轻量备选活动，用于天气变化、体力波动或临时想休息时替换。
  - 在“目的地评价与评分”中规定：
    - 使用综合多源网络评价形成结论，优先参考旅游平台、地图评分、游记/内容社区、媒体/论坛口碑。
    - 每个核心目的地需给出一个标准化分数，例如 10 分制或 5 分制，并给出简要评分依据。
    - 每个地点都要列出优点、缺点、适合停留时长、适合人群、可能踩雷点。
    - 当信息不足、口碑两极分化、明显受季节影响时，必须标注“争议/不确定性”说明。
  - 在“输出结构”中规定最终回答至少包含：
    - 行程概览：旅行基调、建议总节奏、预算档位理解。
    - 每日安排：半天级时间块、建议停留时长、松紧说明。
    - 目的地评分表：地点、推荐分、建议停留时间、亮点、短板、适合时段。
    - 交通建议：跨城/市内移动建议与减少疲劳的做法。
    - 住宿建议：住哪类区域更省心、为何建议住这里。
    - 弹性建议：可删减项、下雨替代项、累了可直接取消的低优先级项目。
    - 温馨提醒：预订、排队、天气、休息窗口。
  - 在“markdown 富文本要求”中规定：
    - 使用分级标题、表格、引用提示块、短列表来呈现。
    - 避免单纯大段散文；强调结构化与可读性。
    - 默认采用中英双语小节标题或关键字段，正文可中文为主并辅以英文关键词。
  - 在“示例”中提供一个完整示例，展示预算问询、评分表、弹性安排和优缺点输出方式。

## Assumptions & Decisions
- 决策：Skill 为“通用旅行规划”，不是某一次固定行程模板。
- 决策：Skill 默认输出风格为中英双语，其中结构标题与关键字段可双语呈现，主体解释优先中文。
- 决策：默认规划粒度为半天级，不提供小时级硬性排程，避免行程过死。
- 决策：默认必须包含交通建议与住宿建议；预算不预设，若缺失则先问。
- 决策：评分基于综合多源网络评价，不绑定单一平台。
- 决策：当评价冲突或信息不足时，不隐藏不确定性，而是显式说明争议来源与适用条件。
- 假设：执行阶段允许联网搜索，以便 Skill 在说明中明确“基于实时网络评价汇总”这一能力和调用策略。
- 假设：当前不需要为该 Skill 额外编写 spec/checklist/tasks 文档，交付目标仅为 `SKILL.md`。
